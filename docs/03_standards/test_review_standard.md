# テスト・レビュー規約 — aituber

## 1. 実装完了の定義

以下をすべて満たした場合にのみ「実装完了」とみなす。

- [ ] `pytest` が通過する
- [ ] `ruff check` でエラーなし
- [ ] `ruff format --check` で差分なし
- [ ] 正常系が確認されている
- [ ] 異常系が確認されている（不正入力・外部 API エラー）
- [ ] ログで問題を切り分け可能である
- [ ] DB 操作がある場合はロールバック・コミットが正しく動く
- [ ] 確認結果が `docs/06_test/` に記録されている

---

## 2. レビュー観点

### 2.1 API 設計

- [ ] レスポンスが Pydantic スキーマで定義されているか
- [ ] エラー時に適切な HTTP ステータスコードと `detail` が返るか
- [ ] 入力バリデーションが行われているか

### 2.2 ドメインロジック

- [ ] `app/core/` が外部依存なしで動作するか
- [ ] 責務が単一になっているか
- [ ] 型ヒントが全関数に付いているか

### 2.3 DB 操作

- [ ] セッションが `get_db` 経由か
- [ ] N+1 クエリが発生していないか
- [ ] トランザクション境界が適切か

### 2.4 外部 API 連携

- [ ] タイムアウト設定があるか
- [ ] リトライ処理があるか（TTS クライアント等）
- [ ] エラーレスポンスが適切にハンドリングされているか

### 2.5 テスト

- [ ] 正常系・異常系のテストがあるか
- [ ] 外部依存がモック化されているか
- [ ] テスト名から内容が分かるか

---

## 3. テストケース作成方針

各機能について最低限以下の 2 系統を作成すること。

- 正常系
- 異常系（不正入力・外部 API エラー）

### テスト命名規則

```
test_<対象>_<条件>_<期待結果>

例:
test_generate_event_normal_scene_returns_event
test_generate_event_empty_input_returns_default
test_synthesize_api_timeout_raises_error
```

---

## 4. テストケース記録テンプレート

`docs/06_test/<カテゴリ>/TC_<機能名>.md` に記録する。

```markdown
# TC_<機能名>

## 実施情報

- 実施日: YYYY-MM-DD
- 実施者: <名前>

## 正常系

- 確認内容と結果

## 異常系

- 確認内容と結果

## 未確認

- 未確認項目（次回対応予定等）

## 備考

- 特記事項
```

## 5. パイプライン固有の確認観点

### 5.1 SegmentationService

- [ ] FFmpeg エラー時に適切な例外が返るか
- [ ] 出力ファイルが `MEDIA_ROOT` に保存されるか
- [ ] `segments` テーブルに正しく記録されるか

### 5.2 QwenTTSClient

- [ ] テキスト → wav 生成が成功するか
- [ ] API 障害時のリトライが動作するか
- [ ] 音声長が正しく取得できるか

### 5.3 SubtitleService

- [ ] 音声長と字幕タイミングが一致するか（ズレ 0.5 秒以内）
- [ ] SRT ファイルが正しいフォーマットで出力されるか

### 5.4 Composer

- [ ] 音声・字幕・動画が正しく合成されるか
- [ ] 出力 mp4 が再生可能か
